# Задание 2. Загрузка рейтингов в списке отрядов

## Что сделано

- `RatingApi.getRating(id)` эмулирует сетевой запрос: `delay(1500)` и случайный рейтинг от 3.0 до 5.0.
- В `SquadListRepositoryImpl` два способа загрузки рейтингов для всех отрядов:
  - `loadRatingsSequentially`: цикл `for`, каждый запрос стартует после завершения предыдущего;
  - `loadRatingsInParallel`: `ids.map { async { ... } }.awaitAll()` внутри `coroutineScope`.
- В `SquadListViewModel.loadRatings(parallel)` время каждого способа измеряется через `measureTimeMillis`.
- Две кнопки в шапке списка запускают способы по отдельности, рейтинг выводится на карточке отряда («★ 4.2»).

## Замеры

Список из 10 отрядов, задержка одного запроса 1500 мс.

| Способ | Время, мс |
|---|---|
| Последовательно | 15013 |
| Параллельно (`async` + `awaitAll`) | 1508 |

Параллельный способ быстрее примерно в 10 раз (15013 / 1508 ≈ 9.96).

## Выводы

1. **Последовательно.** Время равно сумме времён всех запросов: 10 × 1500 мс ≈ 15 с, и оно растёт линейно с числом элементов. Пользователь видит, как рейтинги появляются по одному.
2. **Параллельно.** Все запросы стартуют одновременно, а общее время близко к времени самого долгого из них: около 1500 мс. Лишние 8 мс это накладные расходы на создание корутин и сборку результата.
3. **Почему параллельно можно без потоков.** `delay` не блокирует поток, а приостанавливает корутину, поэтому десятки корутин ожидают одновременно на одном потоке.
4. **Обработка ошибок.** В `coroutineScope` с `async` сбой одного запроса отменяет остальные и пробрасывает исключение наружу. Если нужно показать часть рейтингов, каждый запрос надо оборачивать в `runCatching` внутри `async`.
5. **Ограничения параллельного способа без лимита.** При сотнях элементов получим сотни одновременных запросов: нагрузка на сервер, лимиты соединений OkHttp (по умолчанию 5 запросов на один хост одновременно, остальные ждут в очереди), рост расхода памяти и батареи. Для больших списков параллелизм стоит ограничивать, например, через `Semaphore` или обработку пачками.
6. **Когда что выбирать.** Последовательный способ нужен, когда запрос зависит от результата предыдущего или сервер не выдерживает нагрузки. Во всех остальных случаях параллельная загрузка с ограничением даёт лучший отклик.

## Замечание о точности

Каждый способ запущен по одному разу, поэтому цифры показывают порядок величин, а не среднее. Для эмуляции с `delay` разброс небольшой, но для реального сервера замер стоит повторять несколько раз.
